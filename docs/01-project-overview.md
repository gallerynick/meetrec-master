# 01 · 项目概览与术语表

---

## 1. 项目目标

交付一款**跨平台桌面软件**，让用户在**不上传录音**的前提下完成会议纪要生产：

1. **录音 / 导入音频** → 2. **本地语音识别** → 3. **关键词优先校正** → 4. **AI 生成结构化纪要** → 5. **编辑导出**

最终交付形态：

- **macOS**：MeetRec Master.app（建议再打成 .dmg）
- **Windows**：MeetRec Master.exe（建议再打包为安装包）

### 1.1 为什么做这件事

| 痛点 | 本项目的解法 |
|---|---|
| 云端 ASR 上传录音有隐私与合规风险 | faster-whisper 完全本地推理，断网可用 |
| 通用 ASR 对人名 / 产品名 / 术语识别差 | 关键词库 + initial_prompt 注入 + 后处理纠错 |
| AI 纪要工具锁定单一厂商、价格与可用性受制于人 | 用户自配 Base URL / API Key / 模型名，双协议覆盖主流服务商 |
| 网页版无法录音、无法管理本地文件 | 原生桌面应用，系统级麦克风与文件权限 |

## 2. 目标用户与核心场景

| 用户 | 场景 | 关键诉求 |
|---|---|---|
| 会议组织者 / 项目经理 | 例会、评审会、需求会 | 关键词（人名、项目代号）不能错，行动项要清晰可跟进 |
| 法务 / HR / 医疗等专业用户 | 高敏感会议 | **录音绝不离开本机**，纪要可导出留档 |
| 技术负责人 / 架构师 | 技术评审、事故复盘 | 术语准确，决定与未决问题分明，Markdown 便于进 Git |

### 2.1 典型会话（首次使用）

1. 启动应用 → 首次运行提示下载 ASR 模型（默认 small，约 480 MB）→ 下载完成
2. 进入「录音」页 → 点击录音 → 会议结束 → 停止
3. 自动进入「转写」页 → 关键词以高亮形式标出，疑似纠错带角标 → 用户可点角标撤销
4. 切换到「纪要」页 → 选择服务商与模型 → 生成 → 得到 5 个固定章节的 Markdown
5. 编辑纪要 → 导出 Markdown / TXT → 保存到用户自选目录

## 4. 非目标（Out of Scope，明确不做）

| 不做 | 原因 |
|---|---|
| Web / WebView / Electron / Tauri 任何形态 | 硬约束 C1 / C2 |
| 云端 ASR（含免费额度方案） | 硬约束 C3 |
| 实时字幕 / 在线同传 | 不是会议「纪要」工具的核心路径，性能与准确率均不达标。技术原因见 §4.1 |
| 多人协作 / 云端同步 / 账号体系 | 单机单用户定位，避免引入后端 |
| 声纹分离 / 说话人区分 | faster-whisper 无此能力，需额外模型与算力，超出范围 |
| 翻译（中↔英） | 转写语言可选中文 / 英文，但纪要不做翻译 |
| 插件市场 / 第三方扩展 | 保持封闭可信的供应链 |
| 移动端 | 交付形态明确为桌面 |


### 4.1 为什么不做实时（流式）转写

用户常问「能不能边说话边出字」。答案是 **v1.0 不做**，原因是技术性的，不是排期问题：

1. **faster-whisper 没有原生流式接口。** `model.transcribe()` 接受的是完整音频数组，逐段处理。没有「喂入音频块、增量输出假设」的 API。
2. **流式的正确做法需要专用模型。** 真正的低延迟流式 ASR 需要 Conformer / Transformer-streaming 架构与 chunk-aware 训练（如 WhisperStream、CTC-Transducer）。Whisper 是 encoder-decoder，编码器必须看到完整 30 秒上下文窗口才能解码，无法在音频未结束时输出可靠结果。
3. **可行的近似方案是「滑动窗口分段转写」**：每积累 5–10 秒音频跑一次转写，丢弃已处理部分。延迟在**秒级到十秒级**，不是毫秒级；且边界处的词容易被截断，准确率低于整段转写。
4. **与热词方案冲突。** 四阶段架构依赖「先有完整基线，再做缺口分析」。流式输出意味着基线在音频结束前不断变化，缺口分析无法收敛。

**v1.0 的正确交互**：录完整场会 → 转写（显示进度与已识别片段，可实时看到增量）→ 校对 → 纪要。转写过程的「增量可见」已经覆盖「实时感」的大部分体验需求，见 [docs/09 §4.1 步骤 2](09-ui-design-spec.md)。

**若未来需要真流式**（v2.x 候选）：新增 streaming engine，接入 whisper.cpp 的 streaming 模式或专门的流式模型，作为**可选引擎**（不参与热词四阶段流程），并在 UI 上明确标注「草稿流式，准确率低于批处理」。

## 6. 关键验收指标（KPI）

| 指标 | 目标 | 度量方式 |
|---|---|---|
| 关键词识别召回率 | ≥ 90% | 关键词在转写中出现次数 / 真值标注出现次数 |
| 热词注入副作用 | WER 退化 ≤ 5% | 有热词 vs 无热词转写的词错误率对比 |
| 自动纠错精确率 | ≥ 90% | 自动替换中被判正确的比例 |
| 转写吞吐（small 模型） | ≥ 0.5× 实时（1 分钟音频 ≤ 2 分钟） | 本机计时，macOS arm64 为基准 |
| AI 请求成功率（有网络） | ≥ 99% | 含自动重试 |
| 应用冷启动 | ≤ 3 秒（模型已缓存） | 启动到主窗口可交互 |
| 测试覆盖率 | ≥ 70% | pytest-cov |
| 崩溃率 | 0 未处理异常 | UI 层异常捕获 + 中文提示 |

## 7. 术语表

| 术语 | 定义 |
|---|---|
| **ASR** | Automatic Speech Recognition，语音识别 |
| **faster-whisper** | SYSTRAN 维护的 Whisper CTranslate2 移植，支持离线推理与 initial_prompt |
| **initial_prompt** | faster-whisper 的转写参数，把一段文本作为解码起点上下文注入，用于偏置识别结果 |
| **热词（关键词）** | 用户维护的人名 / 产品名 / 术语，用于强化识别 |
| **关键词优先识别** | 本项目专有流程 = 识别前 initial_prompt 注入 + 识别后纠错校正 |
| **纠错（校正）** | 识别后把疑似错词按拼音 / 编辑距离相似度替换为关键词 |
| **服务商（Provider）** | 一家 AI 服务接入配置 = Base URL + API Key + 模型名 + 采样参数 |
| **OpenAI 兼容** | 实现 POST /chat/completions 协议的服务商（OpenAI / DeepSeek / 通义 / Ollama 等） |
| **Anthropic 原生** | 实现 POST /v1/messages 协议的 Claude 及兼容网关 |
| **会议项目** | 一次会议的完整产物 = 音频 + 转写 + 关键词上下文 + 纪要 + 元数据 |
| **纪要** | AI 生成并经用户编辑的 Markdown 文档，含 5 个固定章节 |
| **诊断包** | 日志 + 配置（脱敏）+ 环境信息的可分享压缩包 |
| **公证（Notarization）** | Apple 对已签名 macOS 应用的远程完整性验证 |
| **Authenticode** | Microsoft 的 Windows 可执行文件数字签名体系 |
